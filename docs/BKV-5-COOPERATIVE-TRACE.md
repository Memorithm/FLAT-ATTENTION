# BKV-5 bounded cooperative timing trace

Status: **research evidence infrastructure only**. This contract does not demonstrate CPU/GPU overlap, acceleration, physical traffic reduction, model quality, or a production scheduling policy.

`api::bkv5_cooperative_trace` binds caller-observed monotonic timing to one already-qualified `CooperativeSelectionTicket`. The current ticket proves only the prefill/first-decode handoff, so this contract accepts `FirstToken` traces only. `SteadyState` is rejected until a separate steady-state handoff contract exists; first-token evidence cannot be relabeled as steady-state evidence.

The trace records selection readiness, qualified handoff, numerical-consumer start/finish, and an optional complete interval for production of the immediately following Boolean decision. That optional interval carries the Boolean cache generation and the next prefix length. It is accepted only when the generation matches the qualified ticket and the prefix is exactly one token beyond the ticket prefix. This prevents timing from an unrelated or non-adjacent Boolean decision from being attributed to the current numerical consumer. All timestamps are unsigned nanoseconds relative to one caller-owned monotonic trace origin; no wall-clock identity is inferred.

Validation fails closed when handoff precedes selection readiness, numerical execution precedes handoff, an interval is reversed, the next-Boolean generation drifts, or the next prefix is not adjacent. A complete identity-bound next-Boolean interval yields the exact interval intersection with current numerical execution. `None` means the interval was not observed; `Some(0)` means the correctly bound interval was observed but did not overlap.

The overlap value is data, not a promotion verdict. The module owns no clock, WGPU submission, CPU worker, thread, queue, transfer, synchronization primitive, scheduler, or benchmark harness. A future BKV-5 qualification must collect this contract from a real target backend, bind device/runtime/source provenance, include transfer and synchronization costs, retain dense fallback, and compare end-to-end first-token and steady-state latency before making any performance claim.
